## 建议执行顺序

分三批，每批之间跑一次完整回归。顺序的判据是「依赖 + 冲突面」，不是严重度。

- 002 / 003 / 004 互不冲突（分别动 `app.css+app.js`、`motion.css`、`motion.js`），可并行派发给不同执行者。

### 第二批（几何与层次，纯 CSS）

`005 → 006 → 007 → 012 → 013`

## 刻意**没有**写成计划的东西

审计过程中确认这些是**作者知情的取舍**，按技能规则「不重新争论已定决策」，不作为问题上报：

- **全局 `*` 降级把 reduced-motion 压到 0.01ms**（`app.css:3817`）—— `motion.css:479` 明确写过这是有意依赖的兜底；改它要连带改 7 个 `motion-*.css` 的降级段。
- **`#code-wrap` 纯淡入无位移**（`motion.css:470`）—— 注释写明「transform 会新建包含块，没必要在这块冒险」。问题在于它**该不该有淡入**，已由 004 处理。
- **全站悬停无 `(hover: hover)` 门控** —— 这是桌面应用（+ 局域网网页），触屏场景证据不足。
- **`.drop-before` 用 animation 而不是 transition** —— 元素是新建的，每次重新生长正是想要的（`motion.css:229-232` 有论证）。
- **运行成功的反馈已存在**（`setStatus('ok') + .mo-flash 720ms`），不报"成功时刻毫无欢愉预算"。

以及这些**假阳性**：全仓 `scale(0)` 0 处；对话框 `scale(.98)` 居中属手册豁免；`motion-lw.css:36` 等处的 `transition: all` **在注释里**（是排查笔记，不是代码）。

### 仍未解决的残留（需要新计划，别硬塞回旧计划）

1. **面板入场与列表首屏填充的窄口子**（承接 011）
   `flushBatch()` 里 `start === 0 && now > 0` 会直接调 `staggerList()`，**不经过** 011 新增的判据。
   若某个列表恰好在面板入场动画的**同一批 mutation 结算**里从 0 项被填成 N 项，子行仍会挂上
   `.mo-stagger`，与面板的 `.mo-enter` 叠成两层 opacity —— 重影在这个窄路径上仍可能复现。
   复现条件苛刻（需要「面板刚出现」与「列表 0→N」落在同一帧批次），但要修就得在该处补同一条判据。

2. **`system-panel.js` 的 6 处 `style.width` 尚未收编**
   它们是系统详情面板里磁盘/内存/缓存占用条的唯一写入方（且从不写 `transform`）。
   要收就得把 6 处一起改成 `transform: scaleX()`，一处漏改就是一条 0 宽的空条。
   该文件是压缩过的单行巨型代码，风险明显高于收益 —— **做之前先单独评估**。

3. **`app.css` 只剩 1 行余量**
   009（四处入场）执行时若顶破 4213，需要先決定：压注释、压成单行、还是上调上限并写明理由。

4. **右键菜单「起始位移方向」在贴底时可能仍是向下 4px**（承接 008）
   `app.js` 的 `showContextMenu()` 顺序是：`menu.hidden = false` → `getBoundingClientRect()`（这一步
   会强制首次样式重算，`@starting-style` 在这里采样 before-change 值）→ **然后**才写
   `--ctx-origin` / `--ctx-start-y`。因此 `transform-origin` 没问题（不参与过渡，晚写也生效），
   但被下边界夹住时那次展开可能仍取到兜底的 `4px`（向下），而不是应有的 `-4px`（向上）。
   **影响**：贴底右键时，菜单的 4px 入场位移方向与实际展开方向相反 —— 4px，肉眼极难察觉。
   **根治方式**：把「测量 + 写变量」挪到 `hidden = false` 之前（需先 `visibility:hidden; display:block`
   量出宽高再显示，并强制一次样式重算）。这会改动定位流程本身，收益 4px ⇒ **暂不值得**。
   真要做，须单独计划并覆盖：贴左/贴右/贴底/正常四种位置的 Feel check。
