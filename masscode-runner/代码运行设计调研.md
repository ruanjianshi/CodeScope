# 代码运行功能设计调研（多语言执行器：架构 / 安全 / 测试）

> 场景定位：本机、单用户、非多租户的开发工具，威胁模型是「自己写的代码失控/资源耗尽」，而非恶意攻击。

## 1 执行后端架构

- **本地直接 spawn**（本项目现状）：也是 VS Code「运行」按钮的事实标准，零隔离、毫秒级启动、零实现成本；风险是失控进程/写盘/网络都在用户权限之内。适合可信代码。
- **Docker 容器**：隔离靠内核 namespaces+cgroups（共享宿主内核，非强隔离），热镜像下每执行数百 ms~秒级。社区自建 OJ 常见此路线（如[《3.从0实现 Online Judge（Docker相关）》](https://www.jianshu.com/p/9338be2f24cc)）。
- **微服务执行器**：[Piston](https://github.com/engineer-man/piston)（Go 实现，语言包做成自包含环境，容器内用 systemd-nspawn 隔离执行）；[Judge0](https://judge0.com/)（最流行开源执行器，默认用 ICPC/IOI 社区沙箱 [isolate](https://github.com/ioi/isolate)（namespace+cgroup+rlimit+seccomp），内置完成的状态枚举，[仓库](https://github.com/judge0/judge0)）。
- **浏览器内**：[WebContainers](https://blog.stackblitz.com/posts/webcontainers-are-here/)（StackBlitz 在浏览器里跑真 Node.js）与 [Pyodide](https://pyodide.org/)（CPython 编译为 WASM）：零后端、天然隔离，但只能覆盖 JS/Python 生态、首次加载需下载 MB 级运行时，多语言全覆盖不现实。
- **远程沙箱/微VM**：[E2B](https://e2b.org.cn/) 基于 [Firecracker](https://firecracker-microvm.github.io/)（约 150ms 启动的微 VM，内核级隔离）提供代码解释 API；[gVisor](https://gvisor.dev/docs/) 用用户态内核拦截 syscall；[nsjail](https://github.com/google/nsjail) 与 [bubblewrap](https://github.com/containers/bubblewrap)（非特权命名空间，Flatpak 在用）是轻量进程沙箱。
- **本机工具怎么选**：业界对「单机个人工具」的标准答案就是本地 spawn + 进程组/资源防护；沙箱只在多租户/不可信代码时引入。

**执行后端方案对比**

| 方案 | 隔离性 | 启动延迟 | 实现复杂度 | 适用场景 |
|---|---|---|---|---|
| 本地 spawn | 无 | ~1–10ms | 低 | 本机个人开发工具（本项目）|
| Docker 容器 | 中（共享内核）| 数百 ms–1s | 中 | 服务端/多租户判题 |
| Piston / Judge0 | 中–高（每执行独立容器/isolate）| 100ms–1s+ | 高（需部署运营）| 在线 IDE 云端执行 |
| WebContainers / Pyodide | 高（无系统接口）| 首次 MB 级下载 | 低–中 | 浏览器内示例/教学 |
| E2B / Firecracker | 高（microVM）| ~150ms | 高 | AI Agent、高安全多租户 |
| nsjail / bubblewrap | 中–高 | ~1–10ms | 中 | Linux 服务端轻量隔离 |

## 2 资源与安全控制

- **进程组与超时**：Node 正确姿势是 `spawn(..., {detached:true})`，此时 child 自成进程组、`child.pid` 即 PGID，超时 `process.kill(-pid,'SIGKILL')` 可杀整组（含孙进程）；更稳的流程是 SIGTERM →宽限 1–2s → SIGKILL，并等待 `close/exit` 事件回收避免僵尸（[child_process 文档](https://nodejs.org/docs/latest/api/child_process.html)）。⚠️ Windows 无 POSIX 进程组信号，`kill(-pid)` 无效，须用 `taskkill /T /F` 或 [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)——这是跨平台执行器最常见的坑。
- **内存/CPU**：POSIX 用 setrlimit 的 RLIMIT_AS/DATA/STACK/CPU/NPROC（[setrlimit(2)](https://man7.org/linux/man-pages/man2/setrlimit.2.html)）；Linux 精确控制靠 [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) 的 memory.max/cpu.max/**pids.max（直接防 fork 炸弹）**。Node 不能直接给子进程 setrlimit，需 `prlimit` 或 `sh -c 'ulimit …'` 包一层。
- **输出流量**：必须流式消费 stdout/stderr——pipe 缓冲满会阻塞子进程，表现为「卡死」而非超时；按字节阈值（64KB~1MB）截断并标注截断，内存只留尾部。
- **文件系统/网络**：服务端典型组合=临时目录可写 + 根只读挂载 + 禁网（[Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/) 的 `--network none`/只读挂载；nsjail 默认禁 net）；防写满磁盘靠 tmpfs/配额。
- **平台差异**：Linux 才谈 cgroup/nsjail/seccomp；macOS 无 cgroup v2，只有 rlimit（sandbox-exec 已废弃）；Windows 用 Job Objects 管 CPU/内存/杀树。单用户工具可忽略沙箱差异，但**杀树差异必须处理**。

## 3 交互与项目管理

- **stdin**：一次性注入（写完 `end()`）适合判题式输入；交互程序（REPL、readline、bash 别名）需 [node-pty](https://github.com/microsoft/node-pty) 伪终端，否则非 tty 时程序行为（缓冲、回显、颜色）不同；流式（WebSocket）是云端 IDE 做法。
- **多文件**：C/C++ 同目录所有 `.c/.cpp` 一起编译；Java 入口=与 public 类同名的文件；include 加 `-I<tmpdir>`。每次运行用**新的子目录**或清空旧产物，避免上次编译产物污染本次（本项目同目录写文件，须注意清理）。
- **依赖**：本机可信场景可允许 npm/pip（代价=污染全局、慢）；在线执行器一律禁网=禁安装。
- **环境探测/降级**：现状「探测→不支持+原因」方向正确，可补充输出安装命令（如 `brew install swift`）。

## 4 错误归一化

- **编译 vs 运行**：按阶段划分——编译期失败（编译器退出非零）与运行期失败（编译成功但运行异常/被信号杀）。Judge0 的状态枚举是现成模板（In Queue→Processing→Accepted/CE/TLE/RE…，[仓库](https://github.com/judge0/judge0)）。
- **编译器输出解析**：gcc/clang `file:line:col: error:`、tsc `error TS2304:`、javac `Main.java:5: error:`，统一解析为 `{file,line,col,severity,message}` 供跳转。
- **行号映射**：TypeScript 运行期栈在编译后 JS 上，需 `tsc --sourceMap`（[tsconfig#sourceMap](https://www.typescriptlang.org/tsconfig#sourceMap)）+ source-map 库把栈帧映射回 `.ts`；C/C++（加 `-g`）/Java 的栈帧自带 `file:line`，无需 source map。

## 5 执行器测试（重点，可直接抄）

**行为测试矩阵**（每条 = 一个测试用例，断言输出/退出码/状态）：

1. **正常输出**：Hello World；无尾换行；多行与空行。
2. **退出码**：`process.exit(3)`→3；非零退出+stderr 有内容。
3. **stdin**：读输入程序，注入多行→预期输出。
4. **argv**：读 `process.argv[2]` 传参→输出参数。
5. **编译失败**：语法错误/未定义变量→状态 CE、输出含 `file:line:col`。
6. **运行期异常**：未捕获异常、断言、除零→非零退出+堆栈。
7. **超时**：`while(true){}`→TLE；**断言进程组无残留**（孙进程也被杀）、临时目录可删、可重跑。
8. **大输出**：打印 2MB→截断生效、不因管道满卡死、有「已截断」标记。
9. **Unicode/编码**：中文/emoji 字节正确；带 BOM 输入。
10. **多文件**：C++ 双文件+头文件链接；Java 跨文件；缺 include→CE 信息完整。
11. **并发隔离**：两运行并发（其一死循环）互不干扰、临时目录不串。
12. **注入/恶意**：代码含 `; | $()`（bash）、路径穿越 `../`、写 `~/.bashrc`、fork 炸弹（资源限制生效）、递归爆栈。
13. **畸形输入**：空代码、纯注释、超大单行、二进制 stdin、缺语言标记。
14. **环境缺失**：藏起某解释器→返回「不支持+原因」。
15. **幂等性**：同代码跑两次逐字节一致；失败后重跑不受残留影响。

**可借鉴实现**：[Judge0 的集成测试与状态断言](https://github.com/judge0/judge0)、[Piston 的 Go 集成测试/示例脚本](https://github.com/engineer-man/piston)、[VS Code 用 vscode-test 起真实扩展宿主做集成测试](https://github.com/microsoft/vscode-test)（[官方 CI 文档](https://code.visualstudio.com/api/working-with-extensions/continuous-integration)）。要点：真实子进程的行为必须**真跑真断言**，lint/单测替代不了；测试里可用短超时（如 200ms）加速；直接断言「杀树」（`kill(-pid)` 后检查残留）与「管道满不死锁」这两个最容易回归的点。

## 6 运行按钮与结果面板的行业约定

- **VS Code**：编辑器右上 ▶ Run + 输出/终端面板（等宽、自动滚动、可复制），终端有 ⬛ 停止按钮杀进程树——本机工具的基准体验。
- **在线 IDE**（[StackBlitz](https://stackblitz.com/)、[CodeSandbox](https://codesandbox.io/)）：终端/预览面板，Run 常自动触发（实时预览）。
- **判题平台**：状态徽标 + 耗时/内存 + 用例 diff。
- 建议面板元素：输出区（等宽/可复制/自动滚动）、**退出码 + 耗时(ms)**、超时/截断标记、运行中 spinner + 停止按钮（映射到杀进程组）、清空按钮、stderr 独立红色区。

## 7 对本项目的建议

**必须做（正确性/稳定性）**
1. 超时改为「SIGTERM→宽限→SIGKILL(-pid)」并等 close 回收；**补 Windows 分支**（`taskkill /T /F` 或 Job Objects）——现实现 `kill(-pid)` 在 Windows 上无效。
2. stdout/stderr 流式消费 + 字节截断（如 1MB）并标注——否则大输出会把「管道写满」伪装成卡死。
3. 每次运行新建子目录、跑完先杀进程再 `rm -rf` 清理（Windows 文件锁）。
4. 错误归一化：编译期/运行期分开，编译器输出解析为结构化 `{file,line,col,msg}`。
5. 落地 §5 行为矩阵 1–15，做成自动化回归。

**应该做（体验）**
- 环境缺失时给安装命令；面板显示耗时/退出码；解析结果回馈编辑器做行号跳转；TS 开 sourceMap 映射栈帧；加停止按钮与截断提示。

**可选（安全加固）**：本机单用户「跑自己的代码」场景，容器/nsjail/cgroups 全可省——威胁模型里没有恶意代码。但**不能省**的底线：进程组超时杀树（防失控+防僵尸）、临时目录隔离（防串扰/污染工程）、输出截断与管道消费（防内存耗尽/死锁）。若将来服务化/多用户，最低成本升级=Docker（`--network none` + 只读根 + memory/pids 限额），再往上才考虑 nsjail/isolate/E2B。

## 与本项目现状的差距

针对 CodeScope 真实现状（runnerFor 注册表、spawn+detached+`kill(-pid,'SIGKILL')`、mkdtemp 临时目录、多文件同目录、单文件复制 10s 超时、TTL 30min 自动回收+启动清扫、单流 2MB 截断、片段名防穿越、Java stdin/cwd 修正、tests/run.js 43+ 用例）逐条对照：

**已达业界基线（本机工具场景，无需改动）**
- **进程组杀树**：`detached:true` + `kill(-pid,'SIGKILL')` 符合 §2 进程组规范，Linux/macOS 下正确，且优于很多同类工具（不少只 kill 单进程导致孙进程残留）。tests/run.js 已有「超时与进程回收」用例覆盖。
- **临时目录**：每次 `mkdtempSync` 新目录 + 多文件同目录（C/C++ 编译链接）+ 单文件复制 10s 超时（防大文件/异常卡死）+ TTL 30 分钟自动回收 + 启动清扫，超出 §3 基线（多数工具只清理不回收）。
- **输出控制**：流式消费 + 单流 2MB 截断并标记，符合 §2/§5-8；stdin 一次性注入后 end 符合 §3 判题式标准。
- **环境探测**：`supported`/`check` + 缺失原因返回，符合 §3 降级约定。
- **安全健壮性**：片段名去除路径分隔符与上跳、防路径穿越（§5-12 已落地）；Java 运行修正 stdin 与 cwd（§3 多文件工程的正确性项）。
- **测试基线**：43+ 用例覆盖 §5 矩阵 1–15 的绝大部分维度（基础执行/stdin/错误与退出码/超时回收/接口契约/安全健壮性/并发/幂等与临时目录），已达标。

**缺口与优先级**（对照 §2–§5 基线逐条判定）

| # | 缺口 | 现状 vs 报告基线 | 本机单用户优先级 |
|---|---|---|---|
| 1 | Windows 杀树分支 | `kill(-pid)` 在 Windows 无效（§2），现状无 `taskkill /T /F`/Job Objects 分支 | **必须**（若声明支持 Windows；否则应在文档中声明仅 POSIX 平台）|
| 2 | 超时终止流程 | 现直接 SIGKILL，无 SIGTERM→宽限→SIGKILL 两级流程（§2） | 应该（跳过清理钩子可能留下未写完的文件/半成品；bash 脚本尤其）|
| 3 | close/exit 回收确认 | SIGKILL 后是否显式等待 close 收尸、并发下是否会积累僵尸，未见实现细节 | 应该（用例已断言无残留，需确认实现侧处理）|
| 4 | 错误归一化 | 有「错误与退出码」测试，但无统一「阶段枚举（OK/CE/RE/TLE）」与 `{file,line,col,msg}` 结构化解析（§4） | 应该（结果面板可读性 + 前端可做行号跳转）|
| 5 | TS sourceMap 栈映射 | tsc 未开 sourceMap，TS 运行期栈指向编译后 JS 行号（§4） | 应该（TS 是核心语言，纠错体验收益最大）|
| 6 | 截断标记 | 2MB 截断已实现，需确认结果中带「[输出已截断]」标记 | 应该（不标注易被误读为完整输出）|
| 7 | fork 炸弹/磁盘写满 | 无 pids/NPROC 限制、无 tmpfs 配额（§2） | 可选（本机可信代码可省；成本低，想防呆可加 `ulimit -u`/`-f`）|
| 8 | 网络禁用 | 无（bash 可出网）（§2 服务端基线） | 可选（本机个人工具按 §7 可省）|
| 9 | PTY 交互 stdin | 一次性注入已满足判题式；交互式 bash/REPL 不支持（§3） | 可选（node-pty 引入原生依赖，性价比低）|
| 10 | rlimit/cgroup 内存限额 | 无（§2） | 可选（§7：单用户场景可省；超时+截断已兜住主要失控路径）|

**结论**：本项目「不能省的安全底线」——进程组超时杀树、临时目录隔离与回收、输出流式消费与截断——已全部就位，**必须做**仅剩 Windows 平台分支一项（取决于平台支持声明）；**应该做**四项为两级终止流程、错误归一化、TS sourceMap 映射、截断标记，均为体验/可调试性收益；其余安全加固（rlimit/cgroup、网络禁用、fork 炸弹防护）在本机单用户威胁模型下可省略，未来服务化或多用户时再按 §7 升级路线补上。
