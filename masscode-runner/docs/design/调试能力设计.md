# CodeScope 调试能力设计（调研 + 方案）

> 状态：**设计稿**（未实现）
> 起因：用户提出「缺少一个很重要的能力 —— 代码的调试，单步运行、断点等等」。
> 本文先查成熟设计，再给出**贴合 CodeScope 现有架构**的落地路径。

---

## 一、成熟设计调研

### 1. VS Code / DAP（Debug Adapter Protocol）

业界事实标准。核心是**三层解耦**：

```
编辑器/IDE  ──DAP(JSON-RPC)──▶  Debug Adapter  ──▶  真正的调试器
   UI                            （每种语言一个）      （pdb / gdb / …）
```

关键点，值得抄的：

| 设计 | 为什么重要 |
|---|---|
| **协议与 UI 分离** | 加一门语言 = 加一个 adapter，UI 一行不用改 |
| **能力协商**（`initialize` 返回 `supportsStepBack` 等） | 有的调试器不支持反向执行，UI 要能**按能力降级**，而不是假装支持 |
| **事件驱动**（`stopped` / `output` / `terminated`） | 调试是**异步**的：程序随时可能停下、输出、退出 |
| **请求-响应 + 事件双通道** | `setBreakpoints` 是请求，`stopped` 是事件，两者不能混 |
| **断点按「源文件+行号」声明，由 adapter 解析** | 前端不需要知道怎么把行号变成内存地址 |

**对我们的启示**：不必实现完整 DAP，但**「能力协商 + 事件驱动 + 断点声明式」这三个思路要抄**。

### 2. Jupyter / JupyterLab 的调试器

- 内核侧用 **`debugpy`**（微软出的 DAP 实现），JupyterLab 前端内置一个 **DAP 客户端**；
- 关键细节：**普通「Run Cell」不触发断点** —— 必须走「**Debug Cell**」；
  因为断点生效要求代码在**被调试的执行路径**里跑。
- 内核是**持久**的，所以调试会话可以跨 cell 保留变量。

**对我们的启示**：CodeScope 的 Python 已经**是持久内核**了（Jupyter 式），
所以「调试」对 Python 来说**门槛最低** —— 缺的只是一个能发调试指令的通道。

### 3. MATLAB / Octave 的命令行调试器

两者都有**内置调试器**，而且是**纯命令行**的：

| 命令 | 作用 |
|---|---|
| `dbstop in <file> at <line>` | 在某文件某行设断点 |
| `dbstop if error` | 出错时自动停下（**最好用的一条**） |
| `dbstep` / `dbstep in` / `dbstep out` | 单步 / 步入 / 步出 |
| `dbcont` | 继续 |
| `dbquit` | 退出调试 |
| `who` / `whos` | 看当前作用域变量 |
| `dbstatus` | 列出所有断点 |
| `dbclear` | 清断点 |

**已实测（本机 Octave 11，无界面 + 管道输入）**：

```
$ printf 'dbstop in t at 3\nrun t\ndbstep\nwho\ndbstep\ndbcont\n' | octave --no-gui --quiet
stopped in t at line 3 [/tmp/cs-dbg/t.m]
3: c = a + b;
debug> stopped in t at line 4 [/tmp/cs-dbg/t.m]
debug> Variables visible from the current scope:
a  ans  b  c
debug> 3
```

✅ **结论：无界面下完全可用**，而且**只要给它 stdin 就能驱动** ——
这正是 CodeScope **已有的真 PTY 终端**能提供的东西。

> ⚠️ **实测补充（重要，别想当然）**：
> - `dbstop in <file> at <line>` + `run` —— **管道输入下可用** ✓（上面已验证）；
> - 但 **`dbstop if error` + `run` 在管道下没有停下** ✗ ——
>   错误直接抛出、会话就结束了，没给 `debug>` 提示符。
>   猜测：它需要**真 TTY**，或者只在**函数调用栈内部**出错才生效
>   （脚本顶层出错可能不走这条路径）。
> - ✅ **实现前必须先用真 PTY 复验这一条** ——
>   CodeScope 的终端就是真 PTY（大概率没问题），
>   但**不能拿管道的结论去推断 PTY 的行为**。
>
> 顺带记一个「调试器能力差异」的例子：`dbstep in`（步入）在
> **脚本顶层**是没有意义的（没有可步入的调用），UI 上该按**当前栈深度**
> 决定置灰与否 —— 这正是 DAP「能力协商」思想在命令行调试器上的对应物。

## 二、CodeScope 的现状（决定了方案）

| 能力 | 现状 | 对调试的意义 |
|---|---|---|
| **终端** | ✅ 真 PTY（WebSocket + xterm） | **可以直接驱动命令行调试器**，这是最大的现成资产 |
| **Python 执行** | ✅ 持久内核（`lib/python-kernel.js`，文件 + sentinel 协议） | 变量跨格保留，天然适合调试 |
| **MATLAB/Octave 执行** | ⚠️ **每次新进程**（`--no-gui`） | 调试**必须**改成「在终端里跑」，否则断点无处安放 |
| **代码编辑器** | ✅ Monaco（装饰、装饰线、光标定位都在用） | 画断点圆点、当前行高亮**已有现成 API** |
| **分段运行** | ✅ `%%` 分节 + 段首分隔线 + 选区运行 | 调试的「按段调试」可以复用这套 |
| **环境检测 / 一键安装** | ✅ 本机管家 | 可以顺带检测 `debugpy` 并一键装 |

**关键判断**：调试**不该另起一套执行通道**，而应该**复用终端**（MATLAB/Octave）
和**现有内核**（Python）。理由：

1. 终端已经是真 PTY，调试器要的 stdin/stdout 语义它天生就有；
2. 用户已经能在终端里手动敲 `dbstep` —— 我们做的只是**把它变成按钮**；
3. 不引入新的进程管理、新的输出通道、新的清理逻辑。

## 三、方案（分两期，先小后大）

### 第一期：**「调试面板 + 命令行调试器」**（推荐先做）

**做法**：不实现 DAP，直接**驱动命令行调试器**，用一套 UI 把命令封装成按钮。

```
┌─ 调试工具条（浮在输出区上方 / 底部面板新增「调试」tab）────────┐
│ ▶ 继续   ⤵ 单步   ⤵↘ 步入   ⤴ 步出   ⏹ 停止   👁 变量        │
└──────────────────────────────────────────────────────────┘
```

**MATLAB / Octave**：

1. 点「🐞 调试本段」→ 切到终端，依次发：
   ```
   dbstop in <file> at <每个断点行>
   run <file>
   ```
2. 终端里出现 `debug>` → 面板按钮映射：
   `继续 → dbcont`、`单步 → dbstep`、`步入 → dbstep in`、`步出 → dbstep out`、
   `变量 → who`、`停止 → dbquit`
3. **断点**：Monaco 行号槽点一下 → 画红点 → 记下 `(文件, 行号)` → 调试时翻译成 `dbstop`。

**Python**：

1. 点「🐞 调试本段」→ 把这一格包成
   ```python
   import pdb; pdb.set_trace()
   <原代码>
   ```
   送进**现有内核**；
2. `pdb` 的提示符 `(Pdb)` 出现在内核 stdout 里 → 面板按钮映射：
   `继续 → c`、`单步 → n`、`步入 → s`、`步出 → r`、`变量 → p locals()`、`停止 → q`。

> ⚠️ **注意**：Python 这条路要处理「内核 stdout 是结构化返回的，不是流式的」——
> 调试是**交互式**的，需要**双向流**。所以 Python 侧更稳的做法是
> **把调试会话也放进终端**（`python3 -m pdb xxx.py`），和 Octave 走同一条路。
> 代价是丢掉内核里已积累的变量 —— 这可以接受（调试本来就该从头跑）。

**优点**：改动小、复用现有资产、能**立刻可用**（尤其是 `dbstop if error`，日常最有用）。
**缺点**：变量查看靠 `who` / `p locals()` 文本输出，不是结构化树；不能改值。

---

### 第二期：**真·DAP 客户端**（Python 优先）

**做法**：实现一个**最小 DAP 客户端**，接 `debugpy`。

```
Monaco(前端) ──▶ CodeScope 调试服务 ──DAP──▶ debugpy ──▶ 用户代码
                      │
                      └─ 复用现有的 SSE 任务通道推事件
```

要点：

1. **`debugpy` 没装** → 正好接到**已有的「一键安装」**里
   （`pip install debugpy`，和今天加的 Octave 动作同一套机制）；
2. **能力协商**：`initialize` 时读 `supportsStepBack` 等，
   不支持的功能**在 UI 上置灰**（别给假按钮）；
3. **断点声明式**：前端只发 `{source, line}`，后端交给 debugpy 解析；
4. **事件复用现有通道**：`stopped` / `output` / `terminated` 走已有的
   **SSE 任务流**（今天已经在用，成熟）；
5. **当前行高亮**：`stopped` 事件带 `line` → 用 **Monaco 装饰**画当前行
   （和 `%%` 段首分隔线同一套 API，已验证可用）。

**为什么 Python 先做**：debugpy 是现成的、协议是标准的、内核已经是持久的。

**MATLAB 不做 DAP**：MathWorks 没有公开的 DAP 适配器，
自研代价太大；**命令行调试器（第一期）就是它的正解**。

## 四、明确**不做**的事（以及为什么）

| 不做 | 原因 |
|---|---|
| 完整实现 DAP 全部请求 | 80% 的价值在 `setBreakpoints` / `stackTrace` / `scopes` / `variables` / `continue` / `next` / `stepIn` / `stepOut` 这 8 个 |
| 反向执行 / 时间旅行调试 | Octave 和 pdb 都不支持；要做只能上 rr 这类工具，和本项目量级不匹配 |
| 内存/寄存器级调试 | 这是脚本语言的教学/科研工具，不是 gdb 前端 |
| 给 MATLAB 自研 DAP adapter | 投入产出比极低；命令行调试器够用 |

---

## 五、建议的落地顺序

1. **断点 UI（Monaco 行号槽红点）** —— 独立价值：纯视觉，不动执行链路；
2. **MATLAB/Octave 调试面板** —— 复用终端，`dbstop` / `dbstep` 系列；
3. **`dbstop if error` 的「出错自动停下」开关** —— 日常最实用的一个；
4. **Python 调试（先 `pdb` 走终端，后 `debugpy` + 最小 DAP）**；
5. **变量面板**（`who` / `p locals()` 的结构化解析）；
6. **一键安装 `debugpy`**（接进已有的环境检测动作）。

## 六、留给下一次的开放问题

- 调试会话与「运行」的关系：调试时是否**禁止**普通运行？（建议：允许，但提示）
- 断点存哪：写进 `.md` 的元数据，还是独立的 `.codescope/breakpoints.json`？
  （建议独立文件 —— 断点是**调试状态**，不是文档内容）
- 多文件片段（`.cpp + .hpp`）的断点如何定位？（MATLAB 单文件场景先不处理）
